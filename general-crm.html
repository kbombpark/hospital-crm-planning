1stCRM에서 범용 CRM으로, 코어와 업종 팩으로 나눠 만든다

1stCRM의 기능을 업종과 무관한 코어와 병원 전용 모듈로 분해한다. 병원 팩은 지금 가동 중인 제품 그대로 두고, 새 업종은 코어 위에 팩 하나를 얹는 방식으로 늘린다.

제품 구조

코어는 모든 업종이 쓰는 기능만 가진다. 업종마다 달라지는 것은 팩으로 빼고, 팩은 코어의 확장 지점(커스텀 필드, 이벤트, 화면 슬롯)만 사용한다.

1stCRM 기능 분해

현재 확인된 기능을 코어, 병원 팩, 분리 필요로 나눈 초안이다. 분리 필요는 한 기능 안에 공통 로직과 병원 로직이 섞인 경우다.

기능배치범용화 메모
고객 검색·등록분리기본 프로필·연락처는 코어. 주민번호·건보 자격 등 병원 필드는 팩의 커스텀 필드로 이동.
예약·접수분리예약 슬롯, 담당자, 상태 흐름은 코어. 접수→진료→수납 단계는 병원 팩.
상담·차트분리상담 기록(텍스트·사진·펜)은 코어. 5종 차트 양식과 진료 코드는 병원 팩.
수납분리결제 수단·미수·환불은 코어. 급여·비급여 구분, 영수증 서식은 병원 팩.
처방전·DUR병원 팩의료 규제 기능. 범용화 대상이 아니다. 재인증은 팩 안에서 독립 진행.
친구톡·SMS·단체문자코어채널 어댑터로 추상화. WhatsApp·FB·IG 멀티메시징을 같은 구조에 추가.
자동 메시징 3단계코어시스템 이벤트, 예약 기준, 상담 내용 기반(미방문 윈백)이 이미 규칙 엔진 형태. 트리거 정의만 팩이 등록하게 바꾼다.
통계·리포트코어지표 정의를 팩이 등록하고 화면은 코어가 그린다.

자동 메시징이 이미 규칙 기반이라는 점이 범용화에서 가장 큰 자산이다. 새로 만들 부분이 적다.

코어 데이터 모델 초안

병원의 "환자"를 코어에서는 "고객"으로 부르고, 업종 고유 개념은 팩이 확장한다.

엔티티코어가 가진 것팩이 확장하는 것
Tenant / Branch사업자, 지점, 사용자, 역할업종별 기본 권한 세트
Customer이름, 연락처, 동의 이력, 태그, 유입 경로환자 번호, 건보 자격, 보호자-반려동물 관계
Appointment일시, 담당자, 자원(룸·장비), 상태진료과, 시술 항목, 접수 단계
Interaction상담·통화·메시지 기록, 첨부차트 양식, 사진 비교 도구
Transaction금액, 수단, 미수, 환불급여 구분, 패키지·회원권 차감
Rule / Campaign트리거, 대상 세그먼트, 템플릿, 발송 채널업종별 트리거와 템플릿 묶음

두 번째 업종 선정 기준

후보는 모두 가설이다. 아래 네 가지로 점수를 매겨 하나만 먼저 검증한다.

  • 코어 재사용률: 병원 팩 없이 코어만으로 몇 %가 동작하는가.
  • 기존 접점: 병원 고객사 네트워크, 광고대행 파트너, 진행 중인 계약으로 접근할 수 있는가.
  • 규제 부담: 업종 고유 인증이 필요한가. 병원의 DUR 재인증 같은 일이 또 생기는가.
  • 결제 의사: 월 구독을 낼 현재 지출(마케팅비, 기존 CRM 비용)이 있는가.

동물병원은 병원 팩과 구조가 가장 비슷하고, B2B 영업관리는 지란지교와 이미 대화가 있다. 두 후보부터 점수화한다.

결정이 필요한 것

범용화를 기존 코드 위에서 할지, 새 코어를 만들지

Next.js 전환과 API 마이그레이션은 끝났다. 현행 코드에서 메시징과 규칙 엔진부터 떼어내는 쪽이 일정과 인력에 맞다.

제안: 기존 코드에서 단계적으로 추출. 새 코어 전면 재작성은 하지 않는다.

고객사별 DB 분리를 코어에서도 유지할지

현재는 고객사마다 DB가 따로 있다. 멀티테넌트 단일 스키마로 가면 팩 추가가 쉬워지지만 이관 비용이 크다.

제안: 신규 업종 팩은 새 테넌트 구조로 시작하고, 병원은 이관 시점을 별도 판단.

팩을 별도 제품명으로 팔지

1stCRM은 병원 이미지가 강하다. 범용 코어에 다른 이름을 붙일지 정해야 한다.

제안: 두 번째 팩 파일럿이 성공한 뒤 결정.
